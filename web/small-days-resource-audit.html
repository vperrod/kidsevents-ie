Root cause

Your spec is explicit (and correct):

contract.py  MIN_DESCRIPTION_WORDS = {"event": 60, "place": 120, "holiday": 120}
               # "Words a description needs before it is worth a parent's time, per kind."

phase1b-reresearch-migrate.md §1b:
  "51 of 61 events and all 47 places fail the §2 description word bands
   (median 24/52 words vs a 60/120 floor). Relaxing the bands would re-admit
   exactly that boilerplate. The fix is to run the existing catalogue through the
   real four-step pipeline… using the source_url every record already has."

The four-step write step is told “60–200 words / 120–300 words, using only the facts above, do not invent” (_NO_INVENTING). A 1-sentence caption / a 1-line listing card cannot truthfully yield 60 words, so the model writes honestly short and the gate rejects. The factory then re-runs that same 4-step pipeline on the next thin candidate. Tokens spent → 32-event catalogue. The gate is doing what you specified; the waste is the sources.

Fix — applied & verified

I added a pre-gate short-circuit in factory_worker.promote() (the single function both staging.py:119 and the web discovery cycle call). After the research fetch, before classify/facts/extract/write (the 4 model calls), if the fetched source text is shorter than min(MIN_DESCRIPTION_WORDS) = 60 words, it can't satisfy any kind's floor without inventing — so the gate would reject it on description regardless. It is parked as needs-input (a curator note folded into text via hint can still push it over the floor, so it stays recoverable) and the 4 calls are skipped.

Unit proof: a 7-word source now returns (None, "Source text is only 7 words… below the 60-word minimum…", missing_field="description") with 0 LLM calls — classify/facts/extract/write never ran. A 240-word source still runs the full pipeline. ✅

Savings (measured against the live staged queues): 1,175/1,179 social + 1,023/1,043 web candidates short-circuited → ~8,792 LLM calls spared per sweep. Live now — the running factory cycle was restarted to load the patched code (PID 3782240; journal shows yourdaysout county pages now fetching ✓ HTTP 200).

Fix #2 — applied & verified (the catalogue-growth lever)

  • FETCH_GAP_SECS: 2 → 4 — gentler per-host throttle.
  • Rotating Chrome UAs — a 3-variant desktop-Chrome pool cycled per fetch (Chrome 13x only, so the IG caption scraper still gets server-rendered HTML).
  • 429/503/502 retry-with-backoff in _http_text — honours Retry-After, backs off 3/6/12s, 3 retries; hard 403/404 still raise immediately (no wasted retries).
Verified: (a) a 429 recovers on the 2nd fetch; (b) a 403 raises immediately; (c) a real yourdaysout page now reads 913 words (missing='') where it 429-blocked before; (d) the live cycle (PID 3782240) shows yourdaysout county pages fetching ✓ HTTP 200 at ~1.5s instead of 429. Those readable pages are what let the four-step pipeline write a 60+ word description and clear the gate.
  • Drop the search-gateway junk. The ~43 off-topic domains (India/US/Czech/ booking.com) get discovered + fetched + gate-rejected every cycle — pure overhead. Filter the search lane to Irish (.ie) + verified family sources.
  • Do NOT lower MIN_DESCRIPTION_WORDS. Forbidden by your own spec (§1b) — it would re-admit exactly the boilerplate the gate was built to exclude.
